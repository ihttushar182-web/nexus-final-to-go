# 07 — Internationalisation

**Bangla (`bn`) is the default. English (`en`) is the second language.** Both are
first-class: every customer-facing string exists in both, and a test enforces it.

## 1. How a language is chosen

| Order | Source |
| --- | --- |
| 1 | the `nl_lang` cookie, set when a visitor uses the language toggle |
| 2 | Bangla — the default for a first-time visitor |

`lib/i18n/config.ts` holds the locale list, default and cookie name.
`lib/i18n/server.ts` resolves the locale in server components via `getLocale()`.

## 2. Where strings live

Content is **not** fetched from a translation API. It is typed data:

```ts
export interface LocalizedText { bn: string; en: string }
```

- Page content: the `{ bn, en }` fields in `/data` (products, FAQs, insights, policies…).
- Shared UI labels (buttons, form states): `lib/i18n/dictionaries.ts`, keyed and typed —
  `translate("action.orderNow", locale)` or `createTranslator(locale)`.

Rendering uses the helpers in `lib/utils.ts`:

```tsx
t(product.name, locale)        // single string
tList(product.deliverables, locale)   // list, with a safe empty fallback
```

`t()` and `tList()` never throw on missing data — they return an empty string or an empty
list, so a data gap degrades instead of crashing a page.

## 3. Why one URL and a cookie (and not `/[locale]/`)

A cookie keeps a single URL for both languages: no duplicated route tree, no duplicated
components, and no risk of the two language versions drifting apart. The trade-off is that
pages read a cookie and therefore render dynamically.

**If SEO for each language becomes a priority**, migrate to static `/[locale]/…` routes:
move `app/*` under `app/[locale]/`, add `generateStaticParams` returning `["bn", "en"]`,
prefix internal links with the active locale, and emit `hreflang` alternates in
`app/[locale]/layout.tsx`. Everything else already works, because all content is already
a `{ bn, en }` pair and no component hard-codes copy. Tracked in
`docs/13_OPEN_QUESTIONS.md`.

## 4. Rules for writing copy

- Bangla is the primary voice; English must be a real translation, not a machine-shaped
  afterthought.
- Never leave one language empty — `npm run test` fails on any `{ bn: "", en: "…" }` pair
  anywhere under `/data` or in the dictionaries.
- Numbers, prices and dates: prices use the ৳ symbol via `formatCurrency`; dates go through
  `formatDate(value, locale)`.
- Keep brand terms consistent across languages (see `data/brand.ts`).

## 5. Fonts

Self-hosted in `app/fonts/` via `next/font/local` (`app/layout.tsx`):

| Font | Used for |
| --- | --- |
| Space Grotesk | Latin headings |
| Hind Siliguri | Bangla text (headings and body) |
| Inter | Latin body |

@fontsource packages in `devDependencies` are the source for `scripts/sync-fonts.mjs`,
which copies the woff2 files into `app/fonts/`. This exists because `next/font/google`
requires network access at build time; self-hosting also removes a third-party request
from the critical path.

## 6. Adding a UI string

1. Add the key to `messages` in `lib/i18n/dictionaries.ts` with **both** languages.
2. Use `tr("your.key")` from `createTranslator(locale)`.
3. Run `npm run test` — the dictionary test fails if either language is missing.

## 7. Accessibility of language switching

The toggle in `components/layout/Navbar.tsx` is a labelled control, not an icon-only
button, and `app/layout.tsx` sets `lang` and a `data-locale` attribute so assistive
technology and any future styling can rely on it.

## 8. Placeholder policy

If a business fact is not known in one language, it is **not** invented in that language.
The value is written in both as an explicit *TBC* style placeholder from `data/products.ts`
(`TBC`) and recorded in `docs/13_OPEN_QUESTIONS.md`.
